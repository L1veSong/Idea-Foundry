# 设计逼问方法论

> 用于设计审查阶段。在方案确定但未编码前，逐项逼问暴露盲区。

## 逼问维度（8 类）

| # | 维度 | 核心问题 | 示例 |
|---|------|---------|------|
| 1 | 依赖失效 | 关键依赖不可用时怎么办？ | Ollama 离线、skills_list 扫描失败 |
| 2 | 数据过期 | 缓存的假设过期了怎么办？ | skill 描述升级、A 层规则过时 |
| 3 | 能力边界 | 依赖的组件能力够不够？ | qwen2.5:3b 从 200 个中匹配精度 |
| 4 | 组合效应 | 多个输出之间有冲突/顺序问题？ | 3 个匹配 skill 互有依赖 |
| 5 | 资源浪费 | 重复执行/过度执行？ | 每句话都跑 B 层 |
| 6 | 规则膨胀 | 规则多了会不会互相打架？ | A 层 50 条规则冲突 |
| 7 | 脏数据 | 输入里有残骸/损坏数据？ | 50 个 skill 已损坏 |
| 8 | 自毁风险 | 插件自己崩了影响什么？ | pre_llm_call 插件崩溃 |

## 逼问流程

```
1. 列出设计中的关键依赖、缓存、规则、输入
2. 对每个逐项逼问：如果它坏了/过期了/冲突了，会发生什么？
3. 用 clarify() 让用户逐项决策（A/B/C 选项）
4. 决策落地到设计文档中
```

## 🚨 执行铁则（2026-06-05 实战纠正，不可跳过）

以下规则是逼问流程的强制执行部分，跳过即违规：

1. **每个维度必须独立 clarify()。** 即使某个维度看起来"简单"或"答案明显"，也不可批量跳过或合并处理。用户在维度之间可能需要思考、暂停、或给出口头补充信息——批量跳过剥夺了这个空间。
2. **不允许"快速过"后面的维度。** 无论剩余维度多么简单（如格式确认），每个维度都必须给出独立的 clarify() 选择题。用户纠正（2026-06-05）：批量跳过5-8维度 → "回到1重头开始"。
3. **用户说"暂停" → 立刻停，等待"继续"。** 暂停不意味放弃逼问，是用户在思考或需要补充信息。
4. **逼问结论必须汇总到 plan 文件中。** 每个维度的决策都要有可追溯的记录。
