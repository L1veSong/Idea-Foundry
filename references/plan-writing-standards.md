# 用户计划文档写作标准

> 来源: 2026-06-24 心理物理检测 API 项目全程讨论
> 适用: 任何需要写正式计划文档（plan）的场景

## 核心原则

**计划文档必须解释「为什么」，不只是「是什么」。**

用户多次纠正：交付物列表只写了「是什么」（Go HTTP server、API Key、公网地址），没写「为什么要这个」。专业人员和初学者都需要理解每项决策的原因。

## 文档结构要求

1. **目的/验证点** — 这个阶段要验证什么核心假设？答完哪些问题才算成功？
2. **分阶段原因** — 为什么要分阶段？每一阶段的投入依据是什么？
3. **每个交付物带「为什么」** — 表格加一列，解释这个交付物存在的理由
4. **完成标准** — 可勾选的 checklist，满足才进下一阶段
5. **不做的事 + 原因** — 有意推迟的项要写明原因和放到哪个阶段

## 禁止项

- ❌ 把讨论中的举例（如「和风天气」「高德地图」）放进正式文档
- ❌ 在正式文档里写「全自研」「无合作方」等内部会话用语
- ❌ 只有架构图没有实施步骤
- ❌ 交付物列表只有名字没有理由

## 文档受众

一份计划文档应该同时服务于两种读者：
- **初学者**：能看懂在做什么、为什么这么做
- **专业人员**：能获取技术细节、API 设计、架构决策

降维解释 ≠ 降专业度。术语保留但附解释（可用附录）。
